# DirectoryService — карточки задач

## Назначение карточки

Карточка должна описывать проверяемый результат, а не выдавать исполнителю готовую реализацию.
Она должна быть достаточно узкой, чтобы один разработчик мог реализовать, проверить и провести
через review один законченный vertical slice.

Не создавай карточку во внешней системе без прямого запроса. По умолчанию подготовь draft текста.

## Перед созданием

1. Изучи текущее поведение и связанные files/contracts.
2. Отдели пользовательскую проблему от предполагаемого технического решения.
3. Определи минимальный сквозной результат.
4. Найди зависимости и блокирующие backend/frontend изменения.
5. Проверь, можно ли независимо принять результат по acceptance criteria.

Если карточка содержит несколько независимо проверяемых результатов, предложи разбить её.

## Размер карточки

Одна карточка должна иметь:

- одну основную цель;
- один связный vertical slice;
- один понятный набор acceptance criteria;
- ограниченное число затронутых contracts.

Не объединяй в одну карточку одновременно новый API, дерево, формы CRUD, детальную страницу,
виртуализацию и управление связями. Это epic, который нужно разбить на отдельные задачи.

Пример разбиения дерева подразделений:

1. Backend: pagination root-узлов.
2. Backend: pagination прямых детей узла.
3. Frontend: отображение root-узлов.
4. Frontend: expand и lazy loading прямых детей.
5. Frontend: `Показать ещё` отдельно для каждого parent.
6. Integration/regression tests и обработка ошибок.

## Требования против подсказок

Разделяй:

- `Требование` — observable behavior или обязательный contract;
- `Ограничение` — инвариант, совместимость, производительность или безопасность;
- `Подсказка` — необязательный вариант реализации.

Не записывай Zustand, sessionStorage, Map, конкретный hook или библиотеку как требование,
если пользовательское поведение от этого не зависит. Такие решения исполнитель должен обосновать.

## Шаблон карточки

```md
# <Короткий результат>

## Контекст

Какое текущее поведение или ограничение создаёт проблему.

## Цель

Какой один пользовательский или технический результат должен появиться.

## Scope

- Что входит в задачу.
- Какие слои/contracts разрешено менять.

## Не входит

- Связанные улучшения, которые намеренно откладываются.

## Требования

1. Проверяемое поведение.
2. Проверяемое поведение.

## Acceptance criteria

- Given/When/Then либо однозначный наблюдаемый результат.
- Error/empty/loading behavior, если относится к сценарию.
- Требуемая обратная совместимость.

## Проверки

- Какие automated tests должны доказать результат.
- Какие команды качества должны пройти.

## Зависимости и риски

- Связанные карточки, contracts, migration или риск concurrency/cache.

## Технические подсказки

- Необязательные варианты реализации, если они действительно помогают.
```

## Правила формулировки

- Заголовок описывает результат: `Ленивая загрузка детей подразделения`, а не `Работа с деревом`.
- Используй конкретные сущности и действия.
- Не добавляй требования «на будущее» без текущего сценария.
- Не копируй весь DTO, если достаточно сослаться на существующий contract и перечислить изменение.
- Не обещай endpoint или структуру state до проверки фактического кода.
- В acceptance criteria не используй расплывчатые слова «корректно», «удобно», «быстро» без метрики
  или наблюдаемого результата.
- Отдельно указывай edge cases: empty result, duplicate request, retry, archived entity,
  concurrent update и последняя страница, когда они относятся к сценарию.

## Проверка качества карточки

Перед завершением ответь:

- Можно ли понять цель без знания предполагаемой реализации?
- Можно ли однозначно определить, что задача завершена?
- Можно ли реализовать её одним небольшим PR?
- Не смешаны ли Backend, Frontend и Infrastructure без необходимости?
- Не противоречат ли требования текущему contract?
- Есть ли явно указанный out-of-scope?

Если хотя бы на два вопроса ответ отрицательный, карточка требует уточнения или разбиения.
