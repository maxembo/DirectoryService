# DirectoryService — Git, commits и pull requests

## Общие ограничения

- Не создавай branch, commit, push, merge, rebase, tag или PR без прямого запроса пользователя.
- Перед Git-операцией проверь repository root, текущую branch и `git status --short`.
- Не включай несвязанные пользовательские изменения.
- Не используй `git add .` или `git add -A` вслепую; добавляй проверенные paths.
- Не используй `git push --force`. `--force-with-lease` допустим только после явного согласования.
- Не изменяй опубликованную историю через amend/rebase без явного запроса.
- Не коммить `.env`, credentials, secrets, build output и IDE-specific мусор.

## Branch naming

Если существует номер карточки, включай его в branch:

- `feature/DS-F-<number>-<short-kebab-name>`
- `fix/DS-F-<number>-<short-kebab-name>`
- `refactor/DS-F-<number>-<short-kebab-name>`
- `test/DS-F-<number>-<short-kebab-name>`

Если номера нет:

- `feature/<short-kebab-name>`
- `fix/<short-kebab-name>`
- `refactor/<scope>-<short-kebab-name>`
- `test/<short-kebab-name>`
- `docs/<short-kebab-name>`

Используй lowercase kebab-case. Название должно описывать результат, а не процесс работы.

## Подготовка commit

Перед commit:

1. Проверь `git status --short`.
2. Просмотри полный diff и отдельно staged diff.
3. Убедись, что commit содержит одну логически завершённую причину изменения.
4. Удали debug-код, случайное форматирование и временные файлы.
5. Запусти самую узкую релевантную проверку.
6. Добавь только относящиеся к commit файлы.

Если изменение нельзя кратко описать одним результатом, раздели его на несколько commits.
Не дроби один неработоспособный vertical slice на commits, которые по отдельности не собираются,
без конкретной причины.

## Формат commit message

В репозитории используется русский subject с техническим scope:

`<Scope>: <глагол в настоящем времени> <результат>`

Допустимые scopes:

- `Backend`
- `Frontend`
- `Infrastructure`
- `Tests`
- `Docs`
- `Project`

Примеры:

- `Frontend: добавляет ленивую загрузку дочерних подразделений`
- `Backend: стабилизирует пагинацию дочерних подразделений`
- `Tests: покрывает восстановление связей подразделения`
- `Project: добавляет правила работы Codex`

Требования к subject:

- используй один последовательный стиль: `добавляет`, `исправляет`, `удаляет`, `переносит`,
  `стабилизирует`, `покрывает`;
- описывай эффект commit, а не действие разработчика;
- не используй расплывчатые сообщения `fix`, `changes`, `правки`, `готово`, `final`;
- не ставь точку в конце;
- старайся укладываться примерно в 72 символа, но не жертвуй смыслом ради числа.

Текущие сообщения вида `Frontend: исправлена ...` и `Backend: настроено ...` понятны, но смешивают
грамматический стиль. Для новых commits используй форму настоящего времени.

## Commit body

Body нужен, если из subject неясны причина, migration path или важный компромисс.

Укажи:

- почему изменение понадобилось;
- какой contract или invariant изменён;
- как проверено;
- известное ограничение, если оно осталось.

Не пересказывай в body список изменённых файлов.

Ссылку на карточку добавляй в footer:

- `Refs #<number>` — связать без автоматического закрытия;
- `Closes #<number>` — только если commit/PR действительно завершает карточку целиком.

## Pull request

PR должен содержать:

- `Что изменилось`;
- `Почему`;
- `Как проверено` с фактически выполненными командами;
- `Риски и ограничения`;
- ссылку на карточку.

Не заявляй о пройденной проверке, если она не запускалась. Если PR содержит несколько независимых
целей, раздели его до review.

Перед публикацией покажи пользователю branch, staged files, предлагаемый commit message
и проверки. Выполняй commit/push/PR только после прямого запроса.
